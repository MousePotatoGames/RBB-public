# Decision 0002 — 무기 마운트 타입 (표면 / 궤도 / 펫)

- 날짜: 2026-08-05
- 상태: **Accepted** — 2026-08-06 구현 결과 반영 개정 (아래 "구현 후 정정" 참조)
- 관련 규칙: WPN-002, WPN-003, WPN-005, (신설) WPN-007
- 관련 기능: F08 (부착), F09~F11 (무기 3종), 신규 무기

## 맥락

F08까지 무기는 **표면 부착 한 종류**뿐이었습니다. 공 표면에 붙어 공과 함께 회전합니다.

사용자 판단: 이 프로젝트는 **해커톤 출품용 데모**이므로 내용이 풍부해야 하고, CC0 에셋을 도입할 예정입니다. 따라서 무기의 **부착 방식 자체를 다양화**합니다.

## 결정

무기에 **마운트 타입**을 도입합니다.

| 마운트 | 동작 | 예시 |
|---|---|---|
| **Surface** | 공 표면에 붙어 **공과 함께 회전** | 스파이크, 캐논, 테슬라 링 (기존 3종) |
| **Orbit** | 플레이어 주위를 **행성처럼 공전**. 공 회전과 무관 | 공전하는 도끼·검 |
| **Follow** | 플레이어를 **펫처럼 따라다님**. 지연·스프링 추종 | 따라다니는 동물 |

### 부수 결정: 무기 종류 > 슬롯 수

무기 종류를 슬롯 수(3)보다 많게 만듭니다. **매 판 조합 자체가 달라집니다.**

지금은 3종 중 3개를 뽑으므로 순서만 다르고 **획득하는 무기 집합은 매번 동일**합니다. HYP-006(재도전 유도)이 근거로 삼는 "매 판 달라지는 무기"가 실제로는 성립하지 않았습니다.

## 기술 설계

### 핵심 문제

공은 물리로 **계속 회전**합니다. 트랜스폼 자식으로 붙이면 회전을 상속합니다.
표면 무기는 그게 목적이지만(WPN-002), 궤도·펫은 같이 굴러버립니다.

### 마운트별 구조

| | 부모 | 회전 | 갱신 | Rigidbody |
|---|---|---|---|---|
| Surface | Player | 공 회전 상속 | 없음 (트랜스폼 계층) | 없음 |
| Orbit | 컨테이너 (정지) | 자체 계산 (직립) | `FixedUpdate` + `MovePosition` | 키네마틱 + 보간 |
| Follow | 컨테이너 (정지) | 자체 계산 (진행 방향) | `FixedUpdate` + `MovePosition` | 키네마틱 + 보간 |

### 검토했으나 채택하지 않은 대안

**공에 붙이고 매 프레임 역회전**
매 프레임 역쿼터니언을 곱해야 하고, 공 회전 처리가 바뀌면 조용히 깨집니다. 트랜스폼 계층을 쓰는 게 아니라 거스르는 방식입니다.

**플레이어를 따라 움직이는 앵커 오브젝트**
각 무기가 자기 Rigidbody로 플레이어 위치에서 직접 계산하면 앵커가 불필요합니다. 앵커는 오브젝트 하나와 **갱신 순서 의존**을 추가하는데 얻는 게 없습니다.
→ 계층 정리와 일괄 정리를 위한 **정지 컨테이너**만 둡니다 (움직이지 않음).

### 갱신 타이밍 — 가장 중요한 선택

공은 `FixedUpdate`에서 물리로 움직이며 보간됩니다.
무기를 `Update`/`LateUpdate`에서 갱신하면 **시각적으로는 맞지만 물리 쿼리 시점의 위치가 어긋나** 트리거가 헛칩니다.

**채택: 키네마틱 Rigidbody + `MovePosition`(FixedUpdate) + 보간 ON.**
물리는 일관된 포즈를 보고, 렌더링은 보간이 부드럽게 처리합니다.
**`ScrapDrone`이 이미 쓰는 패턴**이므로([Decision 0001](0001-enemy-physics-hybrid.md)) 새 메커니즘이 아니라 기존 패턴의 재사용입니다.

### 콜라이더

- **트리거만, 솔리드 금지** — 궤도 무기가 솔리드면 플레이어와 적을 밀어내 F01~F04 조작 튜닝과 F06 전투가 무너집니다
- **키네마틱만, 다이나믹 금지** — 충돌에 밀려 궤도를 이탈합니다
- 피해 판정이 붙는 시점(F09~)부터 도입. 그 전까지는 콜라이더 없음

### 연산

동시 무기 최대 3개. 궤도는 sin/cos 하나, 펫은 lerp 하나.
**풀링·Job·Burst 전부 불필요합니다.** 그 이상은 과설계입니다.

### 라이프사이클 (실제 위험 지점)

- 궤도·펫 무기는 **플레이어의 자식이 아니므로 플레이어가 죽어도 남습니다.** 현재는 F07의 씬 리로드가 덮지만, 제자리 재시작으로 바꾸면 샙니다
- 파괴된 플레이어를 계속 추종 → 널 참조. **가드 필수**
- 정지 컨테이너 하나로 정리를 `Destroy` 한 번에

### Core 로직 (엔진 참조 없음)

```
OrbitLogic.Position(centre, angle, radius, height)   # 공전 위치
FollowLogic.Step(current, target, speed, dt, trail)  # 지연 추종
```

둘 다 순수 함수 → EditMode 테스트.

## 결과

- 무기 다양성이 **부착 방식 축**으로 확장됩니다
- 무기 종류 > 슬롯 수가 되어 **매 판 무기 조합이 달라집니다** (HYP-006의 실질적 근거)
- CC0 에셋(동물=펫, 중세 무기=궤도)이 자연스럽게 쓰입니다

## 제약 (F09~F11 구현 시 반드시 지킬 것)

**무기 코드가 "나는 공의 자식이다"를 가정하면 안 됩니다.**
`transform.parent`가 공이라고 가정하지 말고 **자기 위치·방향만** 사용할 것. 그러면 마운트가 추가돼도 재작성이 없습니다.

기존 3종은 표면 마운트를 **유지**합니다 — 특히 캐논은 CAN-001의 "공의 회전에 따라 발사 타이밍이 변한다"가 정체성이므로 궤도로 바꾸면 안 됩니다.

## 필요한 규칙 갱신

- **WPN-002** 부착 방향 — 현재 "표면 노멀 정렬 + 공과 함께 회전"이 전제. **마운트 타입별로** 나눠야 합니다
- **WPN-005** 캡슐 무기 종류 — "3종이 중복 없이"를 **"보유 종류 중 슬롯 수만큼 무중복 추첨"**으로
- **WPN-007** (신설) 마운트 타입 정의

## 무기를 데이터로 정의한다 (WPN-008과 함께 결정)

무기 하나 = **ScriptableObject 에셋 하나**. 마운트 타입, 공격 방식, 수치(간격·위력·사거리), 프리팹만 채우면 **코드 없이 새 무기가 만들어집니다.**

근거 — 5종을 늘어놓으면 코드가 필요한 축은 두 개뿐입니다:

| 무기 | 마운트 (WPN-007) | 공격 방식 (WPN-008) |
|---|---|---|
| 크러셔 스파이크 | 표면 | 접촉 |
| 리볼버 캐논 | 표면 | 투사체 |
| 테슬라 링 | 표면 | 방전 |
| 공전 도끼 | **궤도** | 접촉 |
| 추종 펫 | **추종** | 투사체 |

**3 마운트 × 3 공격 = 9가지 조합인데 구현할 코드 경로는 6개**입니다. 이 비율이면 데이터 주도가 이깁니다.

### 다만 프레임워크를 먼저 만들지는 않습니다

기능마다 **정확히 하나씩** 추가하며 자랍니다:

| 기능 | 추가되는 것 | 새로 만드는 무기 |
|---|---|---|
| F09 스파이크 | `WeaponDefinition` SO + **접촉** 공격 + **표면** 마운트 | 스파이크 (에셋 1개) |
| F10 캐논 | **투사체** 공격 + **직선** 이동 + 발사 수·확산 (산탄이 여기서 공짜) | 캐논 (에셋 1개) |
| F11 테슬라 | **방전** 공격 + **즉시(레이저)** 이동 | 테슬라 (에셋 1개) |
| F12 신규 무기 | **궤도·추종** 마운트 (+ 필요하면 **유도** 이동) | 도끼·펫 (에셋 2개, **공격 코드 추가 0**) |

F12 시점에는 새 무기가 **순수 데이터**입니다. 그리고 각 단계는 실제로 쓰이는 것만 만들므로, 검증 안 된 추상화가 남지 않습니다.

### 투사체도 데이터로 (WPN-009)

"투사체가 있냐 없냐 / 초당 발사수 / 발사 형태(레이저·곡선·산탄)"를 전부 조절 가능하게 합니다.
**핵심은 이 중 대부분이 코드가 아니라 수치라는 점입니다.**

코드가 필요한 축은 **이동 방식 3개**뿐입니다:

| 이동 방식 | 코드 | 풀링 |
|---|---|---|
| 직선(Straight) | 속도대로 전진, 수명/사거리로 소멸 | 필요 |
| 유도(Homing) | 직선 + 대상 방향으로 조향 (유도 강도) | 필요 |
| 즉시(Hitscan) | 오브젝트 없이 즉시 판정 = **레이저** | **불필요** |

나머지는 전부 수치이고, 조합만으로 아래가 **코드 추가 없이** 나옵니다:

| 원하는 것 | 설정 |
|---|---|
| 단발 직선 | 직선, 발사 수 1, 확산 0 |
| **산탄** | 직선, 발사 수 5, 확산 30° |
| 유도탄 | 유도, 발사 수 1 |
| 유도 산탄 | 유도, 발사 수 3, 확산 20° |
| **레이저** | 즉시, 발사 수 1 |
| 확산 레이저 | 즉시, 발사 수 3, 확산 15° |

**산탄은 코드 경로가 아닙니다.** 발사 수와 확산 각도를 올린 것뿐입니다 — 이걸 별도 코드로 짜는 게 흔한 낭비입니다.

성능 주의 (기획서 15장):
- 즉시(레이저)는 오브젝트를 안 만들므로 **풀링 자체가 불필요**합니다 — WebGL에서 유리합니다
- 직선·유도는 **반드시 풀링**. 그리고 **발사 수 × 연사가 풀을 고갈시키지 않도록 상한**을 둡니다

### SO 설계 주의

타입별로 안 쓰는 필드가 섞여 40개짜리 신 오브젝트가 되기 쉽습니다.
`[Header]`로 마운트 구역과 공격 구역을 나누고, 툴팁에 **어느 타입에서만 쓰이는지** 명시합니다. 서브에셋 분리는 저작 마찰만 늘리므로 하지 않습니다.

## 구현 후 정정 (2026-08-06, F09~F12 완료 시점)

**이 결정의 핵심 구조는 유지됐습니다** — 무기 = SO 에셋, 마운트 × 공격 방식의 조합,
기능마다 축을 하나씩만 추가. 다만 **구체적인 예측 세 가지가 틀렸습니다.**
지우지 않고 무엇이 왜 달라졌는지 남깁니다.

### 정정 1 — "공격 코드 추가 0"은 절반만 맞았다

| 신규 무기 | 마운트 / 공격 | 예측 | 실제 |
|---|---|---|---|
| 추종 펫 | Follow / 투사체 | 코드 0 | **코드 0** ✅ |
| 공전 도끼 | Orbit / 접촉 | 코드 0 | **새 피해 경로 필요** ❌ |

**펫이 맞은 이유**는 이 문서의 제약을 실제로 지켰기 때문입니다 —
*"무기 코드가 '나는 공의 자식이다'를 가정하면 안 됩니다."*
`ProjectileWeaponController`가 무기의 트랜스폼만 읽으므로, 무기가 공의 자식이 아니어도
그대로 동작했습니다. **제약이 값을 했습니다.**

**도끼가 틀린 이유**는 예측이 "접촉"을 한 덩어리로 봤기 때문입니다.
표면 접촉(SPK-001)은 *본체 충돌 피해의 수식어*라 **공이 적에게 닿아야** 성립합니다.
궤도 도끼는 공이 닿지 않아도 맞혀야 하므로 **독립 피해원**이어야 합니다.
→ 규칙에 [WPN-008a](../Game/GAME_RULES.md)를 신설해 두 경로를 명시했습니다.

**교훈**: "조합만으로 새 무기가 나온다"는 **공격 방식이 마운트에 무관할 때만** 참입니다.
투사체·방전은 무관했고, 접촉은 아니었습니다.

### 정정 2 — 궤도·추종 무기에 콜라이더를 달지 않았다

원래 계획은 트리거 콜라이더 + 키네마틱 Rigidbody + 보간이었습니다.
실제로는 **콜라이더도 Rigidbody도 없이** 반경 판정으로 구현했습니다.

이유는 일관성입니다. F09(원뿔 판정), F10(SphereCast), F11(거리 판정)이 전부
**콜라이더 없이** 판정하도록 각자의 이유로 수렴했습니다. 궤도만 콜라이더를 쓰면
무기 시스템에 판정 철학이 둘 섞입니다. 적 목록은 스포너가 이미 들고 있어 더 싸기도 합니다.

키네마틱 Rigidbody + `MovePosition` + 보간은 **콜라이더가 있을 때** 필요한 구성이었습니다.
콜라이더가 없으면 Rigidbody도 불필요합니다. 갱신 타이밍(`FixedUpdate`)은 그대로 지켰습니다.

**남은 대가**: 보간이 없어 저프레임에서 궤도가 각져 보일 수 있습니다. WebGL에서 확인이 필요합니다.

### 정정 3 — F11의 Hitscan을 만들지 않았다

이 문서는 F11이 *"방전 공격 + 즉시(레이저) 이동"* 을 추가한다고 적었습니다.
**방전만 만들었습니다.** 방전(WPN-008 공격 방식)과 Hitscan(WPN-009 이동 방식)은 다른 것이고,
테슬라는 방전입니다. **Hitscan을 쓰는 무기가 First Playable에 하나도 없습니다.**

이 문서가 스스로 적은 원칙을 따른 결과입니다:

> 쓸 무기 없이 추상화를 먼저 만들면 검증되지 않은 구조가 된다.

같은 이유로 F10에서 조준 보정 코드도 삭제했습니다 (CAN-001 개정으로 소비자가 사라져서).

### 이 정정에서 실제로 배운 것

**예측이 틀린 방향이 일관됩니다** — 전부 "미리 만들어 둘 것"을 과대평가했습니다.
Hitscan, 콜라이더 구성, 접촉의 일반화. 반대로 **제약**(공의 자식을 가정하지 말 것)은
정확히 값을 했습니다.

구조를 미리 정하는 것보다 **경계 조건을 미리 정하는 것**이 수익률이 높았습니다.

## 순서

마운트 **시스템**(궤도·추종)은 F09~F11 이후 신규 무기와 함께 도입합니다.
표면 무기는 마운트가 필요 없고, 쓸 무기 없이 추상화를 먼저 만들면 검증되지 않은 구조가 됩니다.

단, **`WeaponDefinition` SO와 공격 방식 축은 F09부터** 도입합니다 — 나중에 넣으면 F09~F11을 다시 짜야 합니다.
